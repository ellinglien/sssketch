Baseline to hold: 197 files / 3121 tests green, typecheck 0 errors, lint 0 errors + 4

nothing that opens better-sqlite3).

## Task 1 -- the merge/verify script, test first

`scripts/merge-mac-update-feeds.test.ts`, then `scripts/merge-mac-update-feeds.mjs`.

Plain `.mjs`, zero dependencies, on purpose: the merge job is the job that decides whether the
release is correct, and it runs on a runner that has `node` and `gh` preinstalled. Giving it an
`npm ci` would add a couple of minutes and a whole class of install flakiness to exactly the
step that must not flake. `latest-mac.yml` is machine-generated by electron-builder and has a
fixed, tiny shape, so the script parses and re-emits that shape strictly and throws on anything
it does not recognise, rather than pulling in a YAML parser to be liberal with.

Exports: `parseUpdateFeed`, `serializeUpdateFeed`, `mergeMacUpdateFeeds`, `archOfArtifact`,
`verifyUpdateFeed`. CLI: a merge mode (two inputs, one output) and a `--verify` mode.

Tests, including the ones that matter most -- driving the **real installed** electron-updater
(`electron-updater/out/MacUpdater.js`, `.../providers/Provider.js`) over the merged feed, with
`process.arch` forced to `arm64` and to `x64` so the result cannot depend on the host machine.
Both the new naming (passes) and today's naming (proven order-dependent) are covered.

## Task 2 -- arch in every mac artifact name

`electron-builder.yml`: add `mac.artifactName: ${name}-${version}-${arch}.${ext}` and rewrite
the `defaultArch: arm64` comment, whose stated purpose (unsuffixed arm64 names) this
deliberately reverses; it now only decides the local output directory layout.

## Task 3 -- README: changed by nothing, guarded by something

`README.md`'s install section (rewritten in `05623aa`) now carries two version-pinned links at
real v1.3.0 assets. It is **not** edited here: repointing it at `-arm64` names would break the
front page today for the sake of a release that does not exist yet. Instead
`verify-readme-links` (task 4) fails the run when the README's tag, filenames, link text or
architecture coverage do not match the release being built, so it cannot quietly rot.

## Task 4 -- workflow

`.github/workflows/release.yml`:

- in the matrix job, after the build/publish step, upload `dist/latest-mac.yml` as workflow
  artifact `latest-mac-yml-${{ matrix.arch }}` with `if-no-files-found: error`;
- new `merge-update-feed` job, `needs: release`, on ubuntu-latest: download both, merge,
  `gh release upload --clobber`, re-download what is now published, `diff` it against what was
  uploaded, and run `verify` against it with the tag's version and the release's real asset
  list;
- new `verify-readme-links` job, also `needs: release`, running `verify-readme` against
  README.md with the same asset list. Separate job on purpose: a red one there is "the front
  page is stale", not "this build is bad".

## Task 5 -- verify and commit

`npx vitest run`, `npm run typecheck`, `npm run lint`; confirm the three baseline numbers; one
commit in the repo's voice.

## Not in this change, deliberately

- v1.3.0 is not re-published, re-tagged or edited, and the stale v1.2.0 draft is not deleted.
  Both are Elling's call. The half-feed on v1.3.0 stays broken for Intel users until v1.3.1.
- Nothing under `native-engine/`.
- No universal binary, no single-invocation build (see the spec for why that is structurally
  blocked by `extraResources`, not just slower).

## What Elling must check on the first release after this (v1.3.1)

1. The `merge-update-feed` job is green. If it is red, **do not un-draft** -- the message names
   exactly what is wrong. A red `verify-readme-links` is a different, smaller thing: update the
   install section's version and two filenames on master. Best done in the commit that gets
   tagged, so that job is green too.
2. The release has four mac artifacts: `sssketch-1.3.1-arm64.dmg`, `sssketch-1.3.1-arm64.zip`,
   `sssketch-1.3.1-x64.dmg`, `sssketch-1.3.1-x64.zip` (plus blockmaps).
3. `curl -sL .../download/v1.3.1/latest-mac.yml` lists all four, arm64 first.
4. The real end-to-end test that has never been done: an **Intel** Mac running v1.3.0, left
   open, is offered v1.3.1 and installs a build that actually launches. v1.3.0's own feed is
   the arm64-only one, so that machine is being offered an unrunnable build today -- it may
   need v1.3.1 installed by hand first, and then the v1.3.1 -> v1.3.2 update is the honest
   test. Same on an Apple Silicon Mac, where the first update across the rename does a full
   download rather than a differential one (expected, see the spec).
