## 2. What the whole day was about

One problem: **radio's new stem entered audibly late.** It took the previous session five attempts
and this one another five commits. The complete answer, so nobody pays for it a third time:

### It was late *by construction*

Every earlier fix — the rubberband render, the stretch-duration IPC round trip, the engine's
decoded buffer (`preload-stem`), the waveform peaks, the `armRadioPick` ordering bug (`705510a`),
the double push (`f48e7e3`) — was a correct fix to a genuinely cold or genuinely wasteful thing.
Together they made the engine perfect: every change now reads
`setProject 0.0 (decodes 0 of 4 stems) · handler 0.6ms`.

**And the stem was still late**, because `pos` at the engine handler was *always just after a loop
top, never before*: 0.020–0.065 bar warm, up to 0.222 bar cold. Radio decided **at** the boundary,
and commit → React render → stretch resolve → rAF → IPC all ran after the instant the stem should
have started. No renderer optimisation could ever fix that; the work began at zero-hour.

Elling named it before the instrumentation did: *"it hits the end of the loop and expects
everything to happen before it begins again... ideally it should have a loose idea, so it gives
itself enough time to search and load."*

### The fix, in three parts

1. **`b876204` / `c772ec9` — the engine can accept a project early.** `stage-project` /
   `cancel-staged-project`, applied at the loop wrap, sample-accurately.
2. **`e5810f4` — radio decides a lap early.** `radioChangeDueAtNextWrap` pulls the whole decision
   into the preceding lap.
3. **`0c9f440` / `efa6780` — swaps can also land on an arbitrary bar**, closing the mid-loop bare
   cuts that only the wrap case missed.

### The load-bearing insight, if you touch any of this

**The loop top was never exact because it was the loop top.** `Transport::renderLoopAware` already
had to split its block at the wrap, and *that split — a point where no `renderBlock` is in
flight —* is the precondition the whole swap mechanism rests on. Giving an arbitrary bar a split
of the same shape carried the reclamation argument over unchanged. If you ever add a third
landing point, it needs its own split too.

**Reclamation rule, never break it:** park the outgoing snapshot in the retirement slot *first*,
then displace it from `published`, then clear `staged`. Every store must leave its object with
another owner, so `drainRetiredProject()` on the message thread is the last release. If the
retirement slot is occupied at a boundary the audio thread **declines to swap** rather than free
anything.

**No declick on the mid-lap swap, deliberately.** The wrap's 3ms seam fade is right when
everything restarts and wrong mid-lap — it would drag the *unchanged* layers off their own
continuous waveform. A true crossfade would mean rendering the outgoing snapshot after the swap,
which hands the last release back to the audio thread. That trade was explicitly refused. One
layer steps once, at both stems' own loop points.

### Two numbers that were wrong, and the honest ones

`e5810f4` was reported as **95.0% of changes staged**. That simulation did not model two gates the
real `stepRadioStage` has: it never decides early on a tick where a change is already due, nor
while a previous gesture is still armed. **With both modelled: 82.5% before the bar swap, 93.2%
after.** The residue is a change that comes due on the very tick it is noticed — no lead time,
nothing to stage. Pre-existing; closing it means lifting one of those gates, which is a separate
argument about gestures.

**Do not quote the 95%/100% figures.** The simulation lives in the session scratchpad as
`sim/sim2.mjs` and reproduces the baseline; re-run it with both gates if you need a number.

## 4. The UI lesson from this session

The "a change is coming" indicator was built, rejected, and rebuilt **three times in one morning**.
Worth understanding, because the same trap is open elsewhere:

- **v1 (`46c9ddc`)** — a filling rule plus a bar countdown plus an `AT LOOP TOP` chip. Elling:
  *"this bar... what does that mean?"*, *"says 'this bar' but continues to loop for a few more
  times"*, *"yes generally confusing"*.
- The countdown was **actually lying**. It counted `intervalBars`, but the interval is only the
  *earliest* a change may happen — `due` also needs a grid boundary. So it hit zero and sat there
  for laps. And the rule **silently re-based**: it measured the interval while armed and the loop
  while held, same pixels, two meanings, nothing saying so.
- Its track was also the **whole row**, not the waveform column — so the fill fraction was read
  against the wrong span. Geometry error and honesty error were the same bug.
- **v3 (`59d45eb`)**, his idea: *"can't it be the red playhead indicator instead of a progress
  bar?"* — delete the rule, delete the text, breathe the row, let the playhead (which already
  earns its red by carrying audio position) be the "when".

**The lesson: a number the code cannot keep is worse than no number.** The prediction logic was
kept anyway (`radioBarsUntilChange`) because radio's own correctness needs it — the bug was
showing it, not computing it.

One subtlety pinned in a test: `radioBarsUntilChange` deliberately does **not** epsilon-nudge its
"ahead of the playhead" floor, unlike `radioChangeDueAtNextWrap`. `pos` arrives as
`3.999999999998`; the epsilon read a boundary the clock had not crossed as spent, worth two bars of
error one tick before landing. **A boolean can absorb that slack; a number cannot.**

## 5. The hook and replace-soon (`37e55ec`, `a3d3964`, `7350ac0`)

Radio's first real *gesture*, as opposed to a setting. Also the first build of §6.3's turnover
weighting, which nothing had implemented: `even` is now a weighted draw by staleness
(`weight = (staleness + 1) / hold * hurry`), `random` is the same path with base weights pinned
to 1. One code path.

**The three decisions the spec did not make**, all measured rather than asserted:

- **The factor is not symmetrical.** `HOOK_HOLD_FACTOR = 8` divides; `REPLACE_SOON_FACTOR = 4`
  multiplies. A divisor *fights* `staleness + 1`, which grows without bound, so it self-limits. A
  multiplier *compounds* with it — and a flagged layer is by definition already stale. `even`
  alone already hurries a six-turn-stale layer to 47%; ×8 would buy ten points while making every
  unflagged layer wait ~3× a normal turn.
- **"At most one" applies to the hook only.** Two hooks is two centres. Replace-soon makes no
  structural claim, and enforcing uniqueness would mean flagging a second layer silently unflagged
  the first — the row would tell the truth about one channel and lie about another.
- **Replace-soon clears itself; the hook does not.** Different tenses: "keep this for a while" is
  about the future, "replace this one" is about the present stem and dies with it. Cleared in
  `commitSlotPick` — the one place a stem is replaced *by anyone*, so a manual reroll clears it
  too — and at the commit rather than the pick, because a pick can still be withdrawn.

The cycle is **`none → replace soon → hook → none`**, reversed from the obvious order after a test
caught that `none → hook → replace soon` reached replace-soon *through* hook, silently releasing
whatever hook was set on another row.

**What it does by ear**, at `mid` with four channels: a normal layer turns over every ~1:50, a
hooked one every ~4:30 (not 8× — the divisor is climbed each turn by the hook's own growing
staleness), and a flagged one is the very next change 77% of the time, ~96% within two. `even`
itself cuts time-spent-with-something-7-turns-stale from 6.4% to 2.0%, and the worst drought in a
600-turn session from ~18 turns to ~11 — deliberately not zero, because a rotation abolishes
droughts and is audible as a pattern. The padlock still wins over both for free, since
`radioEligibleSlotIds` drops a locked slot before any weight is computed.

**Not on the phone, deliberately.** The wire is cheap but the page is not: the phone row is a fixed
four-column grid with no free cell, so a third key means restructuring it and squeezing the
waveform — a thumb-ergonomics call no agent here can test. Putting it only in the long-press sheet
would let a flag be set that is invisible from the row list, which is the same lying-UI failure
decision 3 exists to prevent. **No wire fields were added either**, per `RemoteRadioView`'s own
rule that a field nothing reads is a lie. This is a clean, well-understood gap if Elling wants it.

  `writeRiffDetail` bumps the `Riffs` write version. Neither fix is small: dropping `COUNT(*)`
  loses delete detection, narrowing the guard changes `isTableSignalCurrent` for every caller.
- **Two pre-existing engine issues, documented and deliberately untouched.** Plain `setProject` can
  already free a snapshot on the audio thread (status quo for every `load-project` ever sent, at

  detached `std::thread` *on the audio thread*; do not copy that pattern.
